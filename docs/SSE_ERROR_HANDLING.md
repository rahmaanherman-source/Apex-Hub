# GODSPEED SSE ERROR HANDLING

This document defines the error-handling contract for the existing APEX Godspeed transport. It is additive and does not create a second SSE client, CommandBus, reducer, or Truth system.

## Error matrix

| Condition | Transport action | Gabby state |
|---|---|---|
| malformed JSON/event schema line | record sanitized diagnostic and continue | remains Active |
| SSE comment heartbeat `: ping` | reset idle timer only | no change |
| `session.ping` | reset idle timer only | no change |
| HTTP 429 | bounded exponential retry | Error only after retries are exhausted |
| HTTP 5xx | bounded exponential retry | Error only after retries are exhausted |
| network failure | bounded exponential retry | Error after retries are exhausted |
| timeout | bounded exponential retry | Error after retries are exhausted |
| idle timeout | retry according to transport policy | Error after retries are exhausted |
| other 4xx | fail immediately | Error |
| stream closes without terminal event | mark incomplete / owner attention | Attention; never Green |
| model text says `done` / `complete` / `success` | ignore as lifecycle signal | unchanged |
| `job.succeeded` | terminal success | Ready / Green |
| `job.failed` | terminal failure | Error / Red |
| `job.cancelled` | terminal cancellation | Neutral / White |

## Retry policy

Default transient retry schedule:

`400ms -> exponential backoff -> maximum 15s -> maximum 5 retries`

Existing APEX configuration takes precedence if a stricter or explicitly configured policy exists.

Retries must not duplicate successful terminal actions. Job identity/idempotency must remain under the existing Godspeed/CommandBus contract.

## Invalid event safety

A malformed event must not crash the stream. Validate structure before it reaches the existing reducer. Diagnostic output must be sanitized and must never echo credentials, API keys, tokens, passwords, private keys, or raw secret-bearing payloads.

Unknown event types are parsed only when structurally valid and are ignored by the reducer unless an explicit verified mapping exists.

## Truth lock

Only an authoritative terminal `job.succeeded` event can transition Gabby to Ready/Green. Text generated by an LLM is not evidence of success. A stream ending without a terminal event is incomplete and cannot be reported as successful.

## Required implementation verification

The implementation agent must inspect the actual project tree before adding tests. The current canonical Apex-Hub repository is a TypeScript/Vite application, not a Flutter package; therefore Dart test files must not be added to this repository unless a real Flutter package is first verified to exist in the repository.

For the current web application, equivalent tests should use the repository's existing JavaScript/TypeScript testing infrastructure if present. If no test runner exists, document that fact and do not claim tests passed.
