# APEX GODSPEED — DIRECT ACTION / COMPUTER USE / AI OPERATOR

**Status:** ADDITIVE / NON-DESTRUCTIVE / CANONICAL ARCHITECTURE ADDENDUM  
**Canonical repository:** `rahmaanherman-source/Apex-Hub`  
**Principle:** THE OWNER SHOULD NOT HAVE TO HUNT.

## 01 — CORE OPERATING LOOP

APEX minimizes human navigation through one continuous task loop:

`OWNER → GABBY → INTENT → SERVICE → ACCOUNT → RESOURCE → EXACT ACTION → EXECUTION METHOD → EXECUTE/GUIDE → VERIFY → RETURN → RECORD`

APEX must preserve the original task whenever an external service or human interaction is required.

APEX must never send the owner to a generic homepage when a verified contextual destination exists.

## 02 — ONE APEX, MANY PROVIDERS

Do not create a second APEX, Gabby, Vault, Truth system, Catalog, Queue, Orchestrator, or Audit system.

External services and capable agents are registered as execution providers inside the existing APEX Service Registry.

Provider examples:

- APEX native tools
- local terminal
- GitHub
- Vercel
- Google AI Studio
- Google Cloud
- AWS
- Shopify
- Stripe
- Supabase
- Google Merchant Center
- Google Ads
- YouTube
- Meta
- TikTok
- UnitedMasters
- authorized browser agents
- authorized computer-use agents
- authorized AI coding agents
- local models

A provider is not considered capable until its capability is discovered and verified.

## 03 — EXECUTION PROVIDER CAPABILITY CONTRACT

Each provider should expose, where technically available:

- provider
- account reference
- project/resource reference
- authorization state
- capabilities
- API capability
- browser capability
- computer-use capability
- local capability
- deep-link capability
- cost tier
- free/included capacity state
- last verified timestamp
- health
- truth state

Never assume a capability exists.

## 04 — SMART EXECUTION ROUTER

Select the safest, most reliable authorized execution path:

1. APEX native action
2. authoritative connected API
3. connected tool
4. authorized local terminal
5. authorized browser/computer-use agent
6. verified exact deep link + owner guidance
7. manual generic instructions only as a last resort

Prefer API/tool execution over UI automation when both can accomplish the same task reliably.
Prefer UI/computer-use only when the required operation is actually UI-bound or when the authorized provider explicitly exposes that capability.

## 05 — EXACT DESTINATION ENGINE

Every actionable issue should resolve to:

`SERVICE → ACCOUNT → PROJECT/RESOURCE → ERROR → EXACT DESTINATION → ACTION`

A destination record may contain:

- service
- account reference
- project
- resource
- page
- action
- URL
- deep link
- authentication requirement
- auth state
- capability
- status
- last verified

Generic service homepages are prohibited when a more precise verified destination exists.

## 06 — DIRECT RESOLUTION

When an owner reports a problem, Gabby should inspect connected state before instructing the owner.

Example:

`OWNER: "Why isn't my deployment working?"`

APEX resolves:

`VERCEL → VERIFIED ACCOUNT → APEX HUB PROJECT → FAILED DEPLOYMENT → ACTUAL BUILD ERROR → DEPLOYMENT LOG → REPAIR/REDEPLOY`

If an authorized execution path exists, use it. Otherwise open the exact verified destination and preserve task state.

## 07 — COMPUTER / BROWSER USE

Where explicit authorization and technical support exist, APEX may use visual computer/browser capabilities to:

- inspect visible UI
- identify controls
- identify errors
- locate settings
- locate forms
- compare actual and expected state
- guide the owner
- perform authorized actions

Never fabricate screen coordinates, controls, fields, or visual state.
If the current interface cannot be reliably interpreted, report that limitation and provide the verified direct destination.

## 08 — VALUE RESOLUTION

When a destination requires a value, search existing authorized sources first:

`APEX DATABASE → VAULT REFERENCE → SERVICE REGISTRY → CONFIGURATION → CANONICAL CATALOG → CONNECTED PROVIDER → AUTHORIZED REPOSITORY`

If the value exists, apply it through the authorized channel without exposing the secret.

If it does not exist:

`IDENTIFY REQUIRED VALUE → IDENTIFY SOURCE → OPEN EXACT SOURCE → OWNER OBTAINS VALUE → RETURN → APPLY → TEST → VERIFY`

Never invent missing values.
Never place secrets in chat, logs, UI, prompts, commits, telemetry, or audit records.

## 09 — RETURN-TO-TASK CONTINUITY

Every external navigation event must retain:

- original task ID
- current step
- blocked step
- required input
- source/destination
- authorization state
- resume action
- verification requirement

After owner interaction, APEX resumes the original task automatically when possible.

## 10 — VOICE / MOBILE OPERATING MODE

Voice and text are command interfaces to the same APEX operator state.

Examples:

- "Fix this."
- "Show me the exact problem."
- "Take me to the exact page."
- "Can you do it yourself?"
- "Use the value already in APEX."
- "Find the missing value."
- "Take me back."
- "Continue where we left off."
- "Verify it."
- "Did it actually work?"
- "Use the cheapest capable model."
- "Use the local model."

The system must not require the owner to remember the external navigation path.

## 11 — API-FIRST / UI-LAST

For every task evaluate:

`CAN API DO IT? → CAN TOOL DO IT? → CAN TERMINAL DO IT? → CAN AGENT DO IT? → CAN COMPUTER USE DO IT? → MUST OWNER DO IT?`

Use the highest-confidence authorized method.

## 12 — AUTHORIZATION BOUNDARY

Automatically permitted where connected and authorized:

- read-only inspection
- health checks
- status checks
- logs
- code analysis
- tests
- safe validation
- diagnostics
- queue status
- preauthorized retries
- reporting

Owner approval remains required for high-impact actions such as:

- financial transactions
- purchases
- advertising spend
- campaign launch
- destructive deletion
- production asset deletion/replacement
- price changes
- account closure
- security downgrades
- other actions with material external impact

## 13 — VERIFY EVERYTHING

Execution is not verification.

Do not declare success because:

- a button was clicked
- an API returned 200
- a job ID exists
- a deployment was created
- an asset ID exists

Instead:

`REQUESTED → EXECUTED → REMOTE STATE CHECK → EXPECTED STATE? → VERIFIED / FAILED`

## 14 — TRUTH STATES

Maintain separate states:

`EXISTS → CONNECTED → AUTHORIZED → FUNCTIONAL → EXECUTED → ACCEPTED → DEPLOYED → LIVE → VERIFIED → PERFORMING → PROFITABLE`

No state may be inferred solely from a prior state.

## 15 — FAILURE RECOVERY

On failure:

1. Preserve current state.
2. Capture the actual error.
3. Classify the error.
4. Identify responsible service/resource.
5. Determine whether APEX can repair it.
6. Attempt safe repair when authorized.
7. Retry when appropriate and idempotent.
8. If owner action is required, resolve the exact destination.
9. Resume the original workflow.
10. Verify the final state.

Never return only "something went wrong."

## 16 — DIRECT ACTION CARD

- status

- owner action required?

`[EXECUTE] [OPEN EXACT PAGE] [SHOW ME] [VERIFY] [RETURN TO TASK]`

Never expose secret values.

## 17 — FREE / LOCAL-FIRST EXECUTION

For AI and compute tasks:

`LOCAL → VERIFIED FREE → INCLUDED → LOWEST-COST CAPABLE → PREMIUM`

Before paid execution:

1. check local capability
2. check verified free quota
3. check included capacity
4. check lower-cost capable providers
5. show cost/alternatives when payment is required
6. obtain required approval

If quota cannot be verified, use `BALANCE_UNKNOWN` rather than inventing a balance.

`DISCOVER → MAP → AUDIT → CLASSIFY → REUSE → INTEGRATE → REPAIR → EXTEND → TEST → VERIFY`

Never blindly rewrite an existing repository.

## 20 — COMMERCE CONTINUITY

## 22 — MASTER PRINCIPLE

**THE OWNER SHOULD NOT HAVE TO HUNT.**

If APEX can do it: **DO IT.**  
If APEX can verify it: **VERIFY IT.**  
If APEX can open the exact place: **OPEN IT.**  
If APEX needs the owner: **TAKE THE OWNER DIRECTLY THERE.**  
If a value exists: **USE THE AUTHORIZED VALUE.**  
If a value does not exist: **FIND THE EXACT SOURCE.**  
If the owner leaves APEX: **REMEMBER THE TASK.**  
If the owner returns: **CONTINUE THE TASK.**  
If something fails: **FIND THE ACTUAL BLOCKER.**  
If something claims success: **VERIFY IT.**  
If a free capable tool exists: **USE IT BEFORE PAYING.**

**PRESERVE → CONNECT → EXECUTE → GUIDE → VERIFY → RETURN → CONTINUE.**
