# APEX UI CHANGE CONTROL LAW

**STATUS: LOCKED**

An owner-approved APEX UI is a protected visual/runtime contract. No AI, developer, framework, dependency, responsive system, or automated process may silently change it.

## HARD RULE
If a proposed or detected change can materially alter the approved UI, STOP BEFORE APPLYING IT and display:

# ⚠️ THIS CHANGE WILL ALTER GABBY'S UI
## ARE YOU COOL WITH THESE CHANGES?

**[ REVIEW CHANGES ]   [ APPROVE ]   [ REJECT ]**

Material change includes layout, spacing, hierarchy, Gabby/orb/chat, typography, icons, colors, materials, animation, controls, navigation, interaction models, viewport behavior, responsive transformations, dependency-induced visual changes, or AI redesign.

Every launch MUST check the approved visual contract for material runtime drift. A mismatch is not permission to redesign. REJECT preserves/restores the approved baseline; APPROVE records owner approval before the new UI becomes authoritative.

When FROZEN, the page/stage cannot scroll, drift, collapse, bounce, or move downward. Only authorized local gestures may move. Any violation is **VISUAL / INTERACTION FAIL — REBUILD FROM CONTRACT**.

Never claim PASS/READY/CONNECTED/VERIFIED without runtime evidence. If evidence is insufficient, show NOT VERIFIED/UNKNOWN.

`REFERENCE → CONTRACT → IMPLEMENTATION → VISUAL COMPARISON → APPROVAL → FREEZE/INTERACTION CHECK → RUNTIME TRUTH → TESTS → RELEASE`
