# APEX MASTER MEMORY PROTOCOL

**Status:** CANONICAL / FOUNDATIONAL
**Scope:** APEX Hub, Gabby, Heritage, connected agents, repositories, builders, audits, and memory systems.
**Authority:** Derived from the approved APEX Master Memory instruction and reconciled against existing APEX memory/security/reality-registry documents.

## 1. MASTER LAW

> KEEP WHAT MATTERS. MERGE WHAT'S THE SAME. ADD WHAT'S NEW. LINK WHAT'S CONNECTED. LEAVE THE REST IN THE ARCHIVE.

Never discard valuable history merely because it is old. Never rebuild a working capability without evidence that rebuilding is required. Never claim completion without verification.

## 2. SEARCH-BEFORE-BUILD MANDATE

Before proposing, coding, configuring, purchasing, or spending builder/API credits:

1. Search the canonical memory records.
2. Search **every relevant accessible APEX repository**.
3. Search repository documentation, contracts, manifests, tests, and evidence.
4. Search related modules and connected repositories.
5. Search audit/reality records.
6. Search current branches/commits where relevant.
7. Search connected builder/deployment state when accessible.
8. Determine whether the requested work already exists.
9. Determine whether it is complete, partial, implemented-but-unverified, deployed, or merely specified.
10. Determine whether another repository is canonical or whether the same capability exists elsewhere.

**A repository search is a required part of every APEX continuation/audit, not an optional convenience.**

## 3. MEMORY RECONCILIATION LOOP

Whenever new information is learned:

`NEW INFORMATION → SEARCH MEMORY + REPOSITORIES → COMPARE → CLASSIFY → KEEP/MERGE/ADD/LINK/ARCHIVE → VERIFY → DOCUMENT`

If the information is already known and unchanged:

`KNOWN → CONFIRM SOURCE → NO DUPLICATE MEMORY → CONTINUE`

If it conflicts with existing memory:

`CONFLICT → PRESERVE BOTH CLAIMS → RECORD SOURCES/TIMESTAMPS/AUTHORITY → VERIFY → UPDATE CANONICAL STATE ONLY WITH EVIDENCE`

Never silently overwrite an older authoritative record.

## 4. MEMORY CLASSES

Every durable record should be classified as one or more of:

- **FOUNDATIONAL** — architecture, principles, security, terminology, mission, non-negotiables.
- **PROJECT** — active products, repos, features, deployments, objectives.
- **KNOWLEDGE** — reusable verified facts, research, technical/market knowledge.
- **USER_APPROVED** — explicit approved preferences, constraints, and operating rules.
- **WORKING** — temporary execution state and active investigations.
- **AUDIT_EVIDENCE** — immutable evidence of checks, findings, timestamps, and unresolved state.
- **ARCHIVE** — historical material preserved for recovery but not active control.

Secrets are never memory.

## 5. TRUTH STATES

Every important claim must carry a state:

`VERIFIED | PARTIALLY_VERIFIED | UNVERIFIED | CONFLICTING | OUTDATED | PROPOSED | ARCHIVED`

Never convert:

- PROPOSED → VERIFIED
- UNVERIFIED → VERIFIED
- PLANNED → COMPLETE
- DESIGNED → BUILT
- BUILT → DEPLOYED
- DEPLOYED → PRODUCTION

without behavioral/evidence-based verification.

## 6. THREE-PASS AUDIT

For major audits and decisions:

### PASS 1 — DISCOVERY
Find everything relevant.

### PASS 2 — VALIDATION
Determine what works, what does not, duplicates, conflicts, gaps, and claims without evidence.

### PASS 3 — SYNTHESIS
Classify:

`KEEP | MERGE | ADD | LINK | ARCHIVE | FIX | VERIFY`

Do not stop after discovery.

## 7. REPOSITORY LAW

APEX Hub is the central coordination shell. Existing repositories are the default implementation home.

Before creating a repository:

- Does one already serve this purpose?
- Can the capability be added there?
- Is another repository canonical?
- Is the new boundary genuinely independent?
- Would it fragment memory/deployment?

For each repository track, when available:

- purpose
- canonical role
- lifecycle status
- dependencies
- related repositories
- deployment target
- branch/state
- tests
- known gaps
- owner
- source-of-truth documents
- integration points

Classify relationships such as `CANONICAL`, `DEPENDENCY`, `SUBSET`, `SUPERSET`, `LEGACY`, `EXPERIMENTAL`, `ARCHIVE`, or `DUPLICATE` only when evidence supports them.

## 8. APEX ARCHITECTURE

Preferred runtime:

`Flutter presentation → CommandBus → Godspeed Runtime → Plugin Bus → Vault Forge → Provider/External Service`

Backend/execution is authoritative. Flutter is a presentation/client layer.

Gabby is the universal human-facing operating interface across APEX modules; she does not replace the specialized modules underneath.

## 9. SECURITY / VAULT LAW

Vault Forge is the canonical credential authority.

No raw credential should be unnecessarily exposed to:

- AI/chat
- frontend/UI
- logs
- durable memory
- knowledge graph
- audit records
- prompts
- repositories/source code

Use credential references and authorized execution through Gatekeeper/Vault.

For integrations distinguish:

`AUTHORIZED → AUTHENTICATED → CAPABLE → TESTED → READ-BACK VERIFIED`

A credential existing or a connection appearing in a UI is not proof of operational verification.

## 10. OBSERVABILITY

Meaningful modules should participate in:

- Health
- Audit
- Notifications
- Metrics
- Documentation
- Knowledge Graph

A feature that cannot report its state is not fully integrated.

## 11. AUDIT FEED VS MEMORY

**Audit Feed:** immutable operational evidence.

**Memory:** durable useful knowledge.

**Knowledge:** reusable understanding.

**Working Memory:** temporary execution state.

**Archive:** historical recoverable material.

Never turn an audit event into durable memory merely because it happened. Retain durable information because it matters.

## 12. KNOWLEDGE GRAPH

Only create relationships supported by source code, documentation, contracts, configuration, dependencies, verified decisions, or explicit statements.

If inferred, mark `INFERRED`.

Never invent relationships to make the ecosystem appear more connected than it is.

## 13. COMPLETION LAW

Lifecycle:

`IDEA → PROPOSED → DESIGNED → IMPLEMENTING → BUILT → TESTED → VERIFIED → DEPLOYED → PRODUCTION → ARCHIVED`

A checkbox is not proof. A build passing is not product verification. A deployed page is not business readiness.

## 14. GAP ENGINE

Every meaningful audit should identify:

1. WHAT EXISTS
2. WHAT WORKS
3. WHAT DOES NOT WORK
4. WHAT IS MISSING
5. WHAT IS DUPLICATED
6. WHAT IS DISCONNECTED
7. WHAT IS OUTDATED
8. WHAT IS UNSAFE
9. WHAT IS UNVERIFIED
10. WHAT CAN BE COMPLETED NOW
11. WHAT REQUIRES HUMAN ACTION
12. WHAT SHOULD BE ARCHIVED

Prioritize the smallest verified set of actions with the highest useful outcome.

## 15. NO-RESTART / NO-DUPLICATE-CREDIT RULE

If part of a job is already complete, preserve it and continue from the verified checkpoint.

Never ask the user to spend credits again on work that was already completed but not surfaced because the system failed to inspect existing work.

If a full-stack requirement reveals missing files/components/integrations, identify them before requesting additional resources.

A suggestion is not a substitute for completing a requirement already explicitly requested.

## 16. BUSINESS EXECUTION

Prioritize:

`REVENUE → PRODUCT → CUSTOMER → DELIVERY → VERIFICATION → SECURITY → SCALE`

Do not allow speculative architecture or cosmetic work to block a verified revenue path.

Do not confuse building the system with using the system.

## 17. LEGAL / IP / FINANCIAL TRUTH

Separate:

`FACT | SOURCE | INTERPRETATION | STRATEGY | PROPOSED ACTION`

Legal, tax, patent, trademark, copyright, ownership, regulatory, financial, and contractual claims require appropriate evidence. Preserve IP history; do not assume a timestamp alone creates legal rights.

## 18. EVOLUTION

Evolution means `KEEP + IMPROVE`, not `DELETE + RESTART`.

When replacing architecture:

1. Preserve the old state/history.
2. Identify compatibility requirements.
3. Define migration.
4. Move functionality.
5. Test.
6. Verify.
7. Retire only after replacement is proven.

## 19. MEMORY COMPRESSION

When memory grows:

- merge repeated facts;
- retain canonical decisions;
- retain current architecture;
- retain historical evidence;
- retain unresolved contradictions;
- archive low-value repetition.

Target: **maximum signal, minimum noise, zero loss of critical knowledge.**
