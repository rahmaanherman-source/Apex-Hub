# APEX Security Operations Implementation Specification

## Mission

Turn the security architecture into a local-first defensive assessment system for authorized penetration testing and security auditing.

## Phase 1 — Read-only foundation

Implement first:

- scope registry
- asset inventory
- check registry
- evidence ledger
- finding model
- JSON report export
- local SQLite persistence
- audit trail
- stop/abort control

No active exploitation in Phase 1.

## Phase 2 — Safe checks

Add deterministic checks for explicitly authorized assets:

- TLS/certificate posture
- HTTP security headers
- DNS/security configuration observations
- exposed service inventory
- dependency/version inventory where source is provided
- repository secret-pattern detection without collecting secret values
- authentication/security configuration review
- API endpoint inventory from supplied specifications

Each check must declare:

`check_id`, `risk_class`, `required_scope`, `destructive=false`, `evidence_schema`.

## Phase 3 — Authorized active testing

Only after the authorization gate is implemented and tested may the platform integrate approved penetration-testing tools. Tool execution must receive a machine-readable scope generated by the authorization layer and must be denied when scope validation fails.

The platform must not implement stealth, persistence, credential theft, destructive actions, or denial-of-service behavior as default capabilities.

## Phase 4 — Remediation verification

For every confirmed finding:

1. record remediation
2. record changed version/commit/configuration reference
3. retest the same security property
4. compare before/after evidence
5. close only when the required evidence passes

## Required local API surface

- `GET /security/status`
- `POST /security/scopes`
- `GET /security/scopes`
- `POST /security/assets`
- `GET /security/assets`
- `POST /security/checks/run`
- `GET /security/findings`
- `POST /security/findings/{id}/remediation`
- `POST /security/findings/{id}/retest`
- `GET /security/evidence/{id}`
- `GET /security/report`

All mutation endpoints require an authenticated local operator context. Active testing additionally requires an `AUTHORIZED` scope.

## Verification requirements

A build is not complete when the API exists. Verify:

- unauthorized target is rejected
- expired scope is rejected
- excluded target is rejected
- disallowed test class is rejected
- emergency stop blocks execution
- evidence is recorded
- secrets do not enter evidence/logs
- remediation changes can be retested
- report states match actual evidence

## Governing loop

REMEMBER → AUDIT → REBUILD → REBOOT → VERIFY

Security loop:

DISCOVER → SCOPE → CHECK → EVIDENCE → FIX → RETEST → VERIFY
